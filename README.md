# Creative Touch Website OS

The Creative Touch Website Production Operating System — the control plane that owns project state,
agents, workflow, approvals, artifacts, knowledge and execution history. Model providers (Claude,
OpenAI, Gemini) are replaceable intelligence behind a neutral interface.

Current phase: **CTOS-002 — Identity + Secure Execution Gateway + First Live Provider Adapter.**

## Run locally

```bash
npm install
npm run dev
```

Open http://localhost:5173

Other scripts: `npm run typecheck`, `npm test` (Vitest), `npm run build` (typecheck + production build),
`npm run verify` (typecheck + tests + build), `npm run preview`.

Without a `.env.local` the app runs in **local mode**: sign in with a name and role, in-memory U-Proof
seed, embedded gateway with stub providers. Copy `.env.example` to `.env.local`, apply both migrations
in `supabase/migrations/`, and set the Supabase values for real identity, persistence and the
server-side execution gateway (`OPENAI_API_KEY` on the gateway enables the first live provider).

Security: `npm run security:scan` builds the bundle with canary secrets and fails if any reaches it.
Gateway: `npm run gateway:check` type-checks the Edge Function under Deno and produces a deployable bundle.

## Stack

React 19 · TypeScript · Vite 7 · TanStack Router (file-based routes) · Tailwind CSS 4 · Radix UI primitives (shadcn-style components in `src/components/ui`) · Lucide · class-variance-authority · React Hook Form · Zod.

TanStack Start was deliberately not used — a plain Vite + TanStack Router SPA keeps the architecture clean and portable.

## Architecture

```
src/
  data/
    types.ts          Core entities (Client, Project, ProjectPhase, Agent, ProjectPage,
                      Ticket, Artifact, QAItem, LaunchHold, Approval, ActivityEvent)
    state-machine.ts  Project state machine + labels, phases, permission model, safety doctrine
    seed.ts           Real U-Proof project seed (no invented dates)
  state/
    os-store.tsx      In-memory store (context + reducer) — the ONLY data source the UI uses
  auth/               Supabase Auth session + local-mode identity, sign-in gate
  schemas/            Versioned Zod output schemas (structured-output validation)
  ai/                 AIProvider interface, ModelRouter, OpenAI live adapter + provider seams
  gateway/            Execution gateway core (auth, permission enforcement, records) + runtime wrappers
  services/
    repository.ts     OSRepository seam + createRepository(); supabase/ holds SupabaseRepository
    artifacts.ts      Versioned artifacts        agent-jobs.ts  Job lifecycle + execution
    handoffs.ts       Agent handoffs             knowledge.ts   Memory scopes + approval rules
    integrations.ts   Execution-plane adapter contracts
  components/
    os/               AppSidebar, PageHeader, status, Pipeline, StatCard, ActivityTimeline,
                      LaunchHoldsPanel, NewProjectDialog, TicketDrawer
    ui/               shadcn-style primitives
  routes/             File-based routes (routeTree.gen.ts is generated by the Vite plugin)
```

### Control plane vs execution plane

This dashboard is the **control plane**: it records project state, tickets, approvals and holds.
Agents and external systems (WordPress, Cloudflare, Google, Meta, hosting) are the **execution plane**
and are not connected yet. "Run Next Ticket" creates a real job, routes it through the ModelRouter to a
stub provider, records runs, produces a versioned artifact and a handoff — nothing calls a real API or a site.

### Safety doctrine

BUILD → PREVIEW → HUMAN DESIGN APPROVAL → QA → FINAL REGRESSION AUDIT → CONTROLLED ACTIVATION TESTING → HUMAN LAUNCH APPROVAL → LIVE

Launch approval never auto-approves on zero QA counts. Approving Launch with open launch holds
requires an explicit confirmation and is recorded in activity as a deliberate human decision.
